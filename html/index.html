OpenShift 4.21 Guardrails

Audit trail, a two-person rule for out-of-band deletion of critical resources, red alerts to email and Microsoft Teams, and recovery, for a cluster running OpenShift GitOps (Argo CD). This page is the entry point; everything else is one click away.

What it solves

On a default cluster a single cluster-admin can delete Argo CD, its namespace, the Application CRD or the audit configuration with one command, and nobody is told. This solution makes that impossible out of band, makes every change attributable, and pages the owning team within a minute when a critical object is deleted, when someone tries, or when someone tampers with the control itself.

Trust model in one sentence A change merged through the repository ruleset (two reviewers, code owners, signed commits, CI invariants) and applied by the Argo CD application or ApplicationSet controller is pre-approved: the GitOps path needs no cluster-side approval and is alerted for PR correlation. Any other write or delete on a critical object, by anyone (oc, console, the Argo CD UI, other controllers, cluster-admin), is out of band and needs a request plus two approvers plus an executor, enforced by a built-in ValidatingAdmissionPolicy that cannot be bypassed by disabling a pod.

How it works, layer by layer

#LayerMechanism
1Identity and RBACIdP groups, JIT platform admins without cluster-admin (no impersonate/escalate/bind), no kubeadmin, least-privilege roles with resourceNames; Tier-B kinds (namespaces, CRDs, OLM, Secrets) untouchable by humans; impersonation only for reads and dry-runs
2Argo CD hardeningSSO, RBAC deny delete/override, fenced AppProject, no cascade finalizers, Git is the source of truth
3Admission policyon-object approvals validated in CEL: request + 2 distinct approvers + executor ≠ approver; label control; GitOps-only mutation
4Self-protectionthe policy's own objects are GitOps-only in every phase, self-healed by Argo CD, and any out-of-band write is a P1 alert
5Audit loggingWriteRequestBodies, forwarded to the SIEM (record) and LokiStack (alerting), encrypted etcd, WORM buckets
6Detection19 Loki rules on the audit stream + 15 metrics rules that keep working if the audit pipeline is blinded
7NotificationAlertmanager 0.29: email + Microsoft Teams (Workflows), no grouping delay, repeats until acknowledged, delivery health alerted
8RecoveryGit, OADP schedules to an object-locked bucket, nightly etcd snapshots, rehearsed restore and break-glass

sequenceDiagram
    participant Git as Git PR, 2 reviewers
    participant Argo as Argo CD controller
    participant H as Human with oc or console
    participant API as kube-apiserver + policy
    participant AM as Email + Teams
    Git->>Argo: merged commit removes a critical manifest
    Argo->>API: delete
    API-->>Argo: allowed, GitOps path
    API-->>AM: warning GitOpsCriticalDeletionApplied, link the PR
    H->>API: oc delete critical object
    API-->>H: 403 GUARDRAIL DENIED, needs request + 2 approvals
    API-->>AM: warning CriticalResourceDeleteDenied
    H->>API: request, approver 1, approver 2, executor deletes
    API-->>H: 200 deleted
    API-->>AM: critical CriticalResourceDeleted, email and Teams
