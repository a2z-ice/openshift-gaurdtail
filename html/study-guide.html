OpenShift 4.21 Guardrails: Study Guide

Audit trail, a two-person rule for out-of-band deletion of critical resources (the GitOps path through a reviewed pull request is pre-approved), red alerting to email and Microsoft Teams, and recovery, for a cluster running OpenShift GitOps. Written so that a working OpenShift administrator can become the person who designs, defends and operates this class of control.

Companion to the repository openshift-administration. File references are relative to its root. Verified against OpenShift 4.21 (Kubernetes 1.34), Alertmanager 0.29.0, OpenShift GitOps 1.19+, OpenShift Logging 6.x, Loki Operator 6.x, OADP 1.5. Placeholders (guardrails.example.com, example-org) are as in the repository.

0 · How to use this guide

The guide is sequential. Chapters 1 and 2 give the problem and the Kubernetes mechanics that the design depends on. Chapters 3 to 10 walk through the eight layers in the order a request meets them. Chapter 13 is a gap analysis: everything that the review of corner cases found missing, with the implementation that was added to the repository. Chapter 14 is a catalogue of every corner case with the observed behaviour and what to do. Chapter 15 is a self-assessment.

Trust model in one sentence A change merged through the repository ruleset and applied by the Argo CD application or ApplicationSet controller is pre-approved (GuardrailConfig.spec.gitopsControllers, exempt, alerted as GitOpsCriticalDeletionApplied). Any other write or delete on a critical object, whoever performs it (oc, console, the Argo CD UI acting as argocd-server, other controllers, cluster-admin), is out of band and needs the two-person rule. Chapter 17 explains the decision and the audit that preceded it.

1 · The problem and the threat model

1.1 What goes wrong without it

An OpenShift cluster running Argo CD has a handful of objects whose deletion is catastrophic and, by default, one command away for anyone with cluster-admin:

CommandConsequenceTime to notice by default
oc delete ns openshift-gitopsArgo CD instance, every Application, every AppProject, repo and cluster credentials gone. Applications with the cascade finalizer delete the workloads they manage on the way out.Minutes to hours, when deployments stop or workloads vanish
oc delete crd applications.argoproj.ioEvery Application object cluster-wide is deleted by the API server itself (CRD deletion cascades). With finalizers present, cascade deletion of workloads.Same
oc delete application my-prod-app (with finalizer)Argo CD deletes every resource the app manages: Deployments, Services, PVCs.Immediately, as an outage
oc delete csv openshift-gitops-operator.v1.19.0 -n openshift-gitops-operatorOperator removed; instance stops being reconciled; next upgrade or repair impossible until reinstalled.Days

Each of these is one identity, one action, no second pair of eyes, and by default no alert. Backups make the cluster recoverable, but recovery is measured in tens of minutes to hours of outage plus the forensic work of finding out what happened.

1.4 The eight layers

request ──▶ [1 Identity/RBAC] ──▶ [3 Admission policy] ──▶ etcd │ ▼ (every request, allowed or denied) [5 Audit log] ──▶ SIEM (record) + Loki (alerting) │ [2 Argo CD hardening] ▼ [4 Self-protection] [6 Detection: audit rules + metrics rules] ▼ [7 Alertmanager ──▶ Email + Teams] [8 Recovery: Git, OADP, etcd snapshots] (independent of all above)

Prevention (1–4), detection (5–7) and recovery (8) are independent: each can fail without taking the others with it. Within detection, the audit pipeline and the metrics pipeline are independent as well. That independence is the single most important property of the design; keep it when you extend it.

2 · Foundations you must master

The design leans on precise behaviour of the Kubernetes API server, RBAC, deletion semantics, audit logging and Argo CD. Get these right and every later chapter becomes obvious.

2.1 The API request path

client ─▶ TLS ─▶ Authentication ─▶ Authorization (RBAC) ─▶ Mutating admission ─▶ Schema validation (who?) (may this identity do this verb on this kind?) (webhooks, defaults) ─▶ Validating admission ─▶ etcd write ─▶ Audit event "ResponseComplete" (VAP + validating webhooks: is THIS request acceptable?)
Authentication produces UserInfo: username, groups, uid, extra. For an OAuth login through the IdP, username is the identity the provider mapped (for OIDC usually the email) and groups include system:authenticated, system:authenticated:oauth and the OpenShift Group objects the user is in. For a service account, system:serviceaccount:<ns>:<name> with groups system:serviceaccounts and system:serviceaccounts:<ns>.
Authorization is a yes/no on (identity, verb, group, resource, namespace, name). RBAC is additive: any matching rule allows. There is no deny rule. The cluster-admin ClusterRole is verbs: ["*"], resources: ["*"], apiGroups: ["*"], and the group system:masters is short-circuited to allowed before RBAC is even consulted.
Admission runs only for writes (create, update, patch, delete, connect). Mutating plugins first (may change the object), then validating plugins (may only accept or reject). ValidatingAdmissionPolicy is an in-process validating plugin: its CEL expressions run inside kube-apiserver with the same request context, for every authenticated identity. Authorization skipping for system:masters does not extend to admission.
Persist, then the audit event is completed with the response code and any annotations that admission plugins attached.
Why this matters RBAC answers "may alice delete argocds?", and for cluster-admin the answer is always yes. Admission answers "may this delete of this object happen now?", and can say no to anyone. That is the entire reason the control is an admission policy and not a role.

2.2 RBAC, cluster-admin and impersonation

  • Verbs: get list watch create update patch delete deletecollection. patch cannot be limited to certain fields. If approvers may patch an object, RBAC lets them patch anything in it; the admission policy is what limits the content.
  • cluster-admin bindings: the default cluster-admin ClusterRoleBinding binds the group system:masters. The installer's system:admin user (client certificate in auth/kubeconfig) is in that group. kubeadmin is a bootstrap user bound to cluster-admin through system:cluster-admins. Both bypass the IdP.
  • Impersonation: a request with headers Impersonate-User / Impersonate-Group (oc --as, --as-group) is authorised for the impersonate verb on users/groups, then processed as the impersonated identity. Admission sees the impersonated identity in request.userInfo, so a policy cannot tell an impersonated approver from a real one. The audit event records both: user is the original authenticated user and impersonatedUser is the identity that was assumed. The audit log is the only place the truth survives, which is why any write via impersonation is alerted.
  • Escalation prevention: RBAC forbids granting permissions you do not hold (except with the escalate verb) and binding roles you cannot bind. cluster-admin holds everything, so it can always grant itself or others; hence changes to privileged bindings are alerted.
Corner case: `system:masters` cannot be restricted by RBAC at all Authorization for that group is decided before the RBAC authorizer runs. The only controls that apply to it are admission and audit. Keep the population of certificate holders in that group at zero (vault the installer kubeconfig).

2.3 How deletion really works

DELETE request → authn → authz (delete verb) → admission with operation: DELETE, oldObject = the current object, object = null → if admitted, the API server sets metadata.deletionTimestamp.
No finalizers → the object is removed from etcd immediately. Finalizers present → the object stays, with a deletion timestamp, until every controller that owns a finalizer removes its entry. Removing a finalizer is an UPDATE (patch) on the object. Anyone with patch can strip finalizers, which is why finalizers are not a security control.
Garbage collection: objects with ownerReferences are deleted by the garbage collector (system:serviceaccount:kube-system:generic-garbage-collector) when the owner is gone (background) or before the owner is removed (foreground). Each of those is a normal DELETE request that passes through admission.
Namespace deletion: the namespace enters Terminating; the namespace controller (system:serviceaccount:kube-system:namespace-controller) lists every resource kind and issues deletecollection/DELETE for each object. Admission sees one DELETE per object. If any is denied, the namespace stays Terminating (the NamespaceContentRemaining condition names the kind).
CRD deletion: deleting a CRD deletes every custom resource of that kind cluster-wide (the CRD gets a customresourcecleanup.apiextensions.k8s.io finalizer while this runs). This is the single most destructive delete available.
deletecollection (oc delete cm -l app=x): the API server converts it into individual deletes for admission; a policy sees each object.
dry-run (--dry-run=server): the full path including admission runs; only the etcd write is skipped. This is how tests probe real critical objects safely.
Corner case: a denied namespace-controller delete wedges the namespace If a namespace contains a critical object and someone deletes the namespace, the namespace is accepted for deletion (it is not itself critical) but the controller cannot remove the critical object and the namespace stays Terminating. This is intended (a namespace deletion must not take a critical object with it). Resolution: run the approval workflow on the object, or remove its critical label through the workflow. Chapter 13 adds a policy that prevents tenants from creating this situation on purpose.

2.4 Audit events

Every request produces an audit event at one of four levels: None, Metadata (who, what, verb, result), Request (+ request body), RequestResponse (+ response body). The audit policy picks the level per rule. OpenShift exposes three profiles via APIServer/cluster: Default (Metadata for everything, except OAuth tokens), WriteRequestBodies (bodies for writes), AllRequestBodies (bodies for reads too), plus customRules per group that take precedence over the top-level profile. Red Hat's policy keeps Secrets, ConfigMaps, Routes and OAuth clients at Metadata even for write profiles so credentials do not land in logs.

Three API servers write audit logs on each control-plane node: kube-apiserver (/var/log/kube-apiserver/audit.log), openshift-apiserver (projects, routes, builds, images) and oauth-apiserver (tokens, identities). A request to oc delete project x hits openshift-apiserver, which deletes the namespace through kube-apiserver with the user's identity preserved.

The event fields the design relies on:

verb                      delete | create | update | patch | get | list | watch
user.username / groups    authenticated identity (after impersonation, the ORIGINAL user)
impersonatedUser.username the assumed identity, only when --as was used
objectRef.{apiGroup,resource,namespace,name,subresource}
responseStatus.code       200/201 allowed, 403 denied by admission or RBAC, 422 invalid
requestObject             the body for writes (WriteRequestBodies)
annotations."authorization.k8s.io/decision"   allow | forbid
annotations."authorization.k8s.io/reason"     which binding allowed it
annotations."validation.policy.admission.k8s.io/validation_failure"   JSON with policy, binding, message (when a VAP validation failed and the binding has Audit)
annotations."<policy-name>/<key>"          custom auditAnnotations from the policy
Corner case: audit annotations are attached even when the request is allowed The policy's auditAnnotations run on every evaluated request, and the validation_failure annotation is added whenever a validation fails and Audit is among the binding's actions, regardless of whether Deny is also present. Phase 1 (audit only) therefore produces complete evidence of what phase 3 would have blocked.

2.5 Argo CD reconciliation

  • An Application points at a Git path; the application-controller (SA openshift-gitops-argocd-application-controller) computes desired vs live state and, with automated sync, applies the diff. Prune deletes live objects that are no longer in Git. selfHeal re-applies Git when live drifts.
  • The cascade finalizer resources-finalizer.argocd.argoproj.io on an Application means "when this Application is deleted, delete everything it manages first". Without it, deleting the Application orphans the resources (they keep running).
  • ApplicationSet.spec.syncPolicy.preserveResourcesOnDeletion: true stops the ApplicationSet controller from adding that finalizer to new Applications it generates; existing ones keep whatever they have.
  • Server-side apply (ServerSideApply=true) makes Argo CD a field manager that owns only the fields present in Git; fields added by others (like approval annotations) are left alone and do not show as drift. With client-side apply, Argo CD compares against last-applied-configuration and extra live annotations are also ignored, but Replace=true would wipe them. Never use Replace on critical objects.
  • Argo CD has its own RBAC (policy.csv) evaluated by argocd-server for UI/CLI actions. A user denied applications, delete there never produces an API request. Argo CD's Kubernetes requests are made by its service accounts, not by the logged-in user, so cluster-side attribution of a UI action is "the argocd-server SA"; the Argo CD audit log (or the Argo CD UI's history) names the human. Keep Argo CD SSO on the cluster's IdP so both names match.
  • Argo CD writes to Application objects in three ways: the application-controller sets status (status subresource), the server sets .operation (a top-level field, not a subresource) when a sync is started from the UI/CLI and adds/removes the annotation argocd.argoproj.io/refresh on refresh; the applicationset-controller creates and updates generated Applications. All three identities must be trusted mutators (Chapter 13, gap G3).

3.1 Why the guardrail is only as strong as identity

The policy trusts request.userInfo.username and groups. If usernames are shared, if groups are hand-edited, or if a super-user can silently become an approver, the two-person rule collapses to one person. So the first layer makes every actor a named human from the identity provider, removes standing super-user access, and makes the remaining super-user paths loud.

3.3 Why RBAC still matters, and the two tiers

The policy only denies; it never grants. RBAC decides who may touch a critical object at all, but it cannot restrict a patch to annotations and cannot select by label. The first audit (Chapter 17) found the original roles granted cluster-wide patch on Secrets, CronJobs, CSVs and Groups to every approver, which is a privilege-escalation kit. The corrected 02-rbac/clusterroles.yaml uses the two tools RBAC has:

  • resourceNames for cluster-scoped objects with known names (the six namespaces, the protected CRDs, the policies and bindings, guardrails-* RBAC, the privileged Groups, APIServer/cluster, OAuth/cluster).
  • Namespaced RoleBindings (rolebindings.yaml) in the platform namespaces for kinds that cannot be enumerated (Argo CD CRs, logging/alerting/backup CRs, named CronJobs and ConfigMaps).
TierKindsOut-of-band deletion pathWhy
A (workflow)Argo CD CRs, GuardrailConfig, policies, guardrails-* RBAC, Groups, APIServer/OAuth, LokiStack/CLF/rules, OADP objects, named CronJobs/ConfigMaps, NetworkPoliciesrequest + 2 approvals + executora patch on these cannot yield code execution or credentials, and the hardened binding blocks spec changes anyway

Approvers get patch on Tier A so they can append their entry; executors get delete; nobody gets either on Tier B. Separating "can approve" from "can execute" into two roles is what makes the executor a third person in practice. The reaper service account is scoped the same way and is no longer a trusted writer.

Corner case: impersonating an approver oc --as=a1@example.com --as-group=gitops-deletion-approvers annotate ... used to be a forged approval. Chapter 18 closes it: humans hold guardrails-platform-admin (no impersonate on userextras), a real session carries authentication markers an impersonator cannot forge, approver status requires the marker, and any non-dry-run impersonated write is denied. Impersonation remains available for reads, oc auth can-i and --dry-run=server.
Corner case: group sync lag A newly added approver is denied until the sync runs (isApprover is false). Check oc get group gitops-deletion-approvers -o jsonpath='{.users}' before assuming a policy bug.

The AppProject guardrails pins sourceRepos to this repository, restricts destinations to the platform namespaces and whitelists exactly the cluster-scoped kinds this repository manages. A compromised application repository therefore cannot deploy a binding that neutralises the guardrail.

Corner case: what happens when Git deletes a critical manifest CI invariants reject known weakenings (a base binding losing Deny, a human in an exempt list); otherwise two reviewers including a security code owner approve, the controller prunes the object (it is a gitopsController) and GitOpsCriticalDeletionApplied reaches Teams. The on-call links it to the PR. A Git-driven deletion without a PR means the controller identity is compromised: treat as CriticalResourceDeleted and check PrivilegedTokenMinted. Deleting the same object through the Argo CD UI is not the Git path: argocd-server is denied.
Corner case: the operator recreates the ArgoCD CR The GitOps operator creates the default ArgoCD/openshift-gitops if it is missing. That is recovery, not a security hole: the CR is name-protected, the operator SA is a trusted mutator (G3) but not exempt from deletion.
Corner case: additional Argo CD instances Namespace-scoped instances in other namespaces have their own service accounts (<instance>-argocd-application-controller and so on). They are not trusted mutators until added to gitopsServiceAccounts, and their CR is only protected if labelled critical in Git (the name rule covers openshift-gitops only).

5.1 ValidatingAdmissionPolicy anatomy

apiVersion: admissionregistration.k8s.io/v1
kind: ValidatingAdmissionPolicy          # the logic (cluster-scoped)
spec:
  failurePolicy: Fail | Ignore           # what happens if an expression errors or params are missing
  paramKind: { apiVersion, kind }        # optional: a parameter object type, exposed as `params`
  matchConstraints.resourceRules[]       # which (group, resource, operations) reach this policy at all
  matchConditions[]                      # cheap CEL pre-filters (cannot use `variables`)
  variables[]                            # named CEL expressions, lazily evaluated, referenced as variables.<name>
  validations[]                          # each must evaluate to true; false = validation failure
    - expression, message | messageExpression, reason (Forbidden | Invalid | ...)
  auditAnnotations[]                     # key + valueExpression (string or null); attached to the audit event
---
kind: ValidatingAdmissionPolicyBinding   # where and how hard it applies
spec:
  policyName
  paramRef: { name | selector, parameterNotFoundAction: Allow | Deny }
  matchResources: { namespaceSelector, objectSelector, resourceRules }   # further narrows the policy's match
  validationActions: [Deny] | [Warn] | [Audit] | combinations

Variables available inside expressions: object (null on DELETE), oldObject (null on CREATE), request (operation, userInfo, resource, namespace, name, subResource), params, namespaceObject, authorizer, variables.

ConceptBehaviour that the design relies on
validationActionsDeny rejects with the message; Warn lets the request through and adds a Warning: header the client prints; Audit lets it through and adds validation.policy.admission.k8s.io/validation_failure to the audit event. They combine, which is what makes the phased rollout a one-field change.
failurePolicy: FailA runtime CEL error (e.g. indexing a missing key without has()) becomes a denial. Safer for a guardrail, but every expression must guard its accesses. A cost-budget overrun is also an error.
parameterNotFoundActionDeny on the labelled binding (fail closed for critical objects). Allow on the named binding, because it matches every namespace/CRD/cluster-RBAC/group/OLM update cluster-wide and a missing GuardrailConfig must never stop OLM or the namespace lifecycle; its absence is alerted instead.
objectSelector in a bindingMatched against the object's labels, either the new object or the old one. Removing the label in the same request still matches; DELETE requests match on the old object.
Subresourcesresources: ["applications"] does not match applications/status. Status updates by controllers never reach the policy, which keeps evaluation cheap and avoids false denials.
Multiple bindingsA request matching two bindings of the same policy is evaluated twice; harmless.
Type checkingThe API server compiles each expression against the schemas of up to ten matched kinds and reports status.typeChecking.expressionWarnings. For a policy matching many kinds, warnings like "undefined field spec" are expected; evaluation uses dynamic typing. Only a compile error in status.conditions is a problem.
Cost budgetEach request has a CEL cost budget; nested list comprehensions over unbounded strings can exceed it. The design caps approvals at 32 entries and compares small structures. G4 adds an alert on error_type="out_of_budget".
No clockThere is no now() in Kubernetes CEL. Time-based rules must live elsewhere (the reaper).

5.2 CEL primer (what the policy uses)

has(object.metadata.labels)                    # field presence; ALWAYS guard optional fields
'k' in map                                     # key presence; ALWAYS guard before map['k']
map['k'] == 'true'
list.exists(x, cond) / list.all(x, cond) / list.filter(x, cond) / list.map(x, expr)
list.size(), list[0], x in list, list1 + list2
string.split(','), string.startsWith('p'), string.matches('^regex$'), list.join(',')
string(n)                                      # int -> string for messages
cond ? a : b                                   # ternary; `cond ? 'text' : null` for optional audit annotations
a && b, a || b, !a                             # short-circuit: `false && error` is false, `true || error` is true
request.operation == 'DELETE' ? oldObject : object
Two habits that prevent 90 % of VAP incidents Never index a map or list without checking presence first, and never touch object in a DELETE path or oldObject in a CREATE path without a guard on request.operation. Under failurePolicy: Fail an unguarded access denies the request.

5.7 The reaper

CEL has no clock, so approvalTTL is enforced by a CronJob (guardrails-system/approval-reaper, every 10 minutes) that lists the Tier-A kinds, parses delete-approvals, and removes entries that are older than the TTL or more than five minutes in the future or unparseable (G2), passing --resource-version so it never clobbers a concurrent fresh approval. Its service account is in reaperUsers, which V3 permits to remove entries and nothing else; its ClusterRole has no delete verb and no access to Secrets, Groups, cluster RBAC or the policies; it is not a trusted writer in the GitOps-only policy; the namespace has a default-deny NetworkPolicy. A stolen reaper token can therefore neither approve, delete, read secrets nor edit privileged objects.

5.9 Admission corner cases

DELETE has no object Every expression that touches object is guarded by request.operation == 'UPDATE' && ...; the security decision always reads oldObject.
Mutating webhooks run first A mutating webhook (for example a policy engine that injects annotations or labels) changes object before this policy sees it. On an approval write that would make "nothing else changed" false and deny the approval. If you run such a webhook, exclude the guardrail kinds from it or extend nonGuardrailAnnotationsUnchanged to ignore the injected keys.
Garbage collector retries forever If a critical object has an ownerReference to a non-critical parent and the parent is deleted, the GC's DELETE is denied every few seconds and CriticalResourceDeleteDenied fires repeatedly with the GC as actor. Do not put ownerReferences on critical objects; if it happens, either approve the deletion or remove the ownerReference through the workflow.
OLM operator upgrades OLM updates Subscriptions and CSVs in openshift-gitops-operator; those kinds are not in the gitops-only policy's constraints, and V3/V4 pass because guardrail annotations are unchanged. Upgrades are unaffected.
Controllers that write labels on critical objects The label-control policy denies a label addition by an untrusted identity. A controller that re-applies an existing label is unaffected (old already had it). A controller that adds it for the first time must be in gitopsServiceAccounts.
Two approvals in one patch Denied: V3 requires exactly one added entry per request, naming the caller. Two humans cannot sign the same request.
Approval by a service account A service account is in system:serviceaccounts:* groups, never in the approver group, so isApprover is false. Automation cannot approve. If you ever need machine approvals (you should not), you would add the SA's group, which the reviewer agent and CI would flag.
Username characters The entry regex forbids | and , in usernames. OIDC emails are fine. If your IdP produces usernames containing those characters, change the separators in the policy, scripts/lib.sh, the reaper and the docs together.
HyperShift / hosted control planes VAP runs in the hosted kube-apiserver identically. Audit log configuration and shipping differ (managed by the hosting platform); the alerting rules need the audit stream wherever it lands.

13 · Gap analysis and implementations

A corner-case review of the original solution found the following gaps. Each was implemented in the repository as described; the study of each gap teaches a general lesson.

G1 · Anyone with patch rights could mark an object critical

Problem. The deletion policy protected labelled objects but nothing controlled who may add the label. A tenant with patch on a ConfigMap in their namespace could label it critical and (a) force the platform team through the workflow for a tenant object, (b) wedge their namespace in Terminating on cleanup, (c) create noise. "Critical" is a platform decision.

Implementation. manifests/03-guardrails/vap-critical-label-control.yaml: a policy on CREATE and UPDATE of the protected kinds, bound with the same label objectSelector (so it costs nothing on unlabelled traffic), with one validation:

!(newLabelCritical && !oldLabelCritical) || isTrusted
# isTrusted = exemptUsers ∪ gitopsServiceAccounts ∪ members of approverGroups
# oldLabelCritical is guarded by request.operation == 'UPDATE' because oldObject is null on CREATE

Follows the phase actions (Audit → Warn → Deny). Argo CD applying the label from Git is allowed; approvers may label by hand; everyone else gets GUARDRAIL DENIED: only Argo CD, break-glass or members of gitops-deletion-approvers may mark an object as critical. Removal stays governed by V2. Test T3.10 / script cases 2b.

Lesson. A marker that changes enforcement is itself a privileged field; control its creation, not just its removal.

G2 · An approver could write a far-future timestamp and never expire

Problem. The reaper removed entries older than the TTL. CEL cannot check time, so an approver could write a1@example.com|2099-01-01T00:00:00Z and keep their approval valid for years (bounded only by the object's lifetime and the request staying unchanged).

Implementation. The reaper (reaper-cronjob.yaml, reap.sh) now also removes entries whose timestamp is more than 5 minutes in the future or unparseable:

if (( NOW - TS_SEC > TTL_SEC || TS_SEC > NOW + 300 )); then expire; fi

A past timestamp only shortens the approver's own validity, which is harmless. Test T6.2 covers it.

Lesson. When a timestamp is supplied by the party it constrains, validate it against a clock they do not control.

G3 · Trusted GitOps identities were incomplete

Problem. Only the application-controller was in gitopsServiceAccounts. Argo CD's server writes .operation and the argocd.argoproj.io/refresh annotation on Applications (UI/CLI sync and refresh), the ApplicationSet controller creates/updates generated Applications, and the GitOps operator reconciles the ArgoCD CR. In phase 4 those writes to critical Applications would have been denied (UI sync broken); in phases 1–3 they would have produced constant ArgoCDDirectMutation noise.

Implementation. The identities are now split: gitopsControllers (application-controller, ApplicationSet controller) are the Git path and exempt; gitopsServiceAccounts (argocd-server, the GitOps operator, and after phase-1 observation External Secrets or Velero) are trusted mutators only. argocd-server must never be a gitopsController because UI/CLI actions are not Git-reviewed; CI enforces that.

Lesson. "Which identities legitimately write this object" is an empirical question; phase 1 exists to answer it. Trusted mutators are not exempt identities.

G4 · No alert if the policy itself errors or runs out of budget

Problem. Under failurePolicy: Fail, a CEL runtime error or a cost-budget overrun denies requests for the wrong reason, silently.

Implementation. manifests/07-hardening-extras/prometheusrule-vap-health.yaml in openshift-kube-apiserver:

GuardrailPolicyEvaluationErrors: rate(apiserver_validating_admission_policy_check_total{policy=~"guardrails-.*", error_type!="none"}[5m]) > 0
GuardrailPolicyNotEvaluating:    zero evaluations of guardrails-critical-delete in 30 min, or metric absent
GuardrailPolicySlow:             p99 apiserver_validating_admission_policy_check_duration_seconds > 50 ms

Lesson. A fail-closed control needs a health signal so "closed" is noticed.

G5 · OAuth token lifetimes were described, not implemented

manifests/07-hardening-extras/oauth-token-config.yaml: accessTokenMaxAgeSeconds: 28800, accessTokenInactivityTimeout: 2h, applied server-side so the IdP configuration in the cluster-config repository is untouched. The OAuth object is critical (config.openshift.io).

G6 · etcd snapshots were described, not implemented

Ship them off-node with your backup agent; snapshots contain every Secret and must be encrypted at rest (see G8).

G8 · Node-level bypass had no technical mitigation

  • apiserver-etcd-encryption.example.yaml: APIServer.spec.encryption.type: aesgcm, so an etcd snapshot or disk image does not expose Secrets. One-time re-encryption of 10–30 minutes.

15 · Self-assessment

Answer without notes; the answers are in details.

1. Why can RBAC not implement "no single person may delete X", even with a carefully written role?RBAC is additive and evaluated per identity; whoever holds delete can delete alone, and cluster-admin/system:masters hold everything and skip RBAC. Only admission can look at the object's state (approvals) and the request together and say no to any identity.
2. On a DELETE request, which CEL variable holds the object and why does the policy read oldObject for UPDATE decisions too?object is null on DELETE; oldObject holds the object. For UPDATE the security decision must be based on the pre-request state so a change made in the same request cannot be used to satisfy the rule.
3. Why does removing the critical label require approvals?Otherwise "unlabel, then delete" is a one-person path. Rule V2 makes removal exactly as hard as deletion.
4. Why is the Argo CD application-controller not in exemptUsers?Exempting it would turn "merge a PR that removes a manifest" into a single-person deletion, with Git review as the only protection. As a trusted mutator it can change objects; as a non-exempt identity its prunes of critical objects are denied and alerted.
5. How does the design enforce approval expiry without a clock in CEL, and what did G2 fix?A reaper CronJob removes entries older than the TTL; the policy lets that identity only remove. G2 made the reaper also remove future-dated or unparseable timestamps so an approver cannot extend their own approval.
6. Which two audit annotations do the alerts key on, and which is present on allowed requests?guardrails-critical-delete/decision (present on every evaluated request on a critical object, allowed or denied) and validation.policy.admission.k8s.io/validation_failure (present when a validation failed and the binding has Audit).
7. What happens when the audit forwarder is stopped, and which alert tells you?Audit-based alerts go blind; the metrics pipeline raises AuditLogIngestionStalled from the Loki distributor metric (and AuditForwarderChanged on the change itself). Argo CD availability alerts continue from metrics.
8. Why two bindings for the deletion policy?The labelled binding uses an objectSelector so ordinary Secret/ConfigMap traffic is never evaluated; the named binding covers low-traffic kinds that carry no label (namespaces, CRDs, policies, groups). The split also limits the blast radius of fail-closed behaviour.
9. A namespace is stuck in Terminating after the guardrail was enabled. Cause and resolution?It contains a critical object; the namespace controller's deletes are denied. Approve the deletion or remove the label through the workflow. G1 prevents tenants from creating this on purpose.
10. Name the residual risks and their compensating controls.R1 impersonation by cluster-admin (JIT admin, P1 alert, audit shows both identities); R2 node/etcd access (SSH lockdown, etcd encryption, exec alert); R3 whether VAP guards its own bindings (RBAC, self-heal, alert); collusion (audit, recertification); alert delivery (default receiver fallback); Logging upgrades renaming fields (test after upgrade).
11. Why group_wait: 0s for guardrail alerts but not for everything?A deletion is a single, immediately actionable event; grouping delay adds nothing. Capacity alerts benefit from grouping to avoid storms.
12. What does parameterNotFoundAction: Deny do and why is it safe here?Requests matched by the binding are denied when GuardrailConfig/default is missing (fail closed). It is safe because the bindings are scoped to labelled objects and a short list of low-traffic kinds, so workloads are unaffected.
13. Which writes does Argo CD's server make to an Application, and why did that matter?.operation on sync and the argocd.argoproj.io/refresh annotation on refresh. Without the server SA in gitopsServiceAccounts, phase 4 would deny UI syncs of critical Applications (G3).
14. How would you add a new kind (say Certificate from cert-manager) to the protected set?Add its group/resource to matchConstraints of the deletion, label-control and gitops-only policies; to the labelled binding nothing (it inherits); to the reaper's resource list; to the approver/executor ClusterRoles; label the objects in Git; add cert-manager's SA to gitopsServiceAccounts if it writes them; extend the test matrix and the docs' rule table; PR with security review.
15. What is the exact three-step sequence to promote from phase 2 to 3 and the one-line rollback?Verify phase-2 exit criteria; PR changing spec.source.path of the guardrails Application to manifests/overlays/phase3-enforce; after merge, smoke-test with a server dry-run delete of the ArgoCD CR (must be denied). Rollback: the reverse PR (emergency: break-glass edits validationActions, alerted).

After the first version of this material was written, two independent reviewers audited the repository without prior context and reported 59 findings; the platform owner then decided the trust model in §17.2. Both changed the design materially and are the reason several chapters above describe controls that did not exist originally. The full findings table and the control-to-test traceability matrix are in docs/16-production-readiness-review.md; this chapter teaches the lessons.

17.2 The trust-model decision

The original design made the Argo CD controller non-exempt, so a manifest removed from Git was still denied on the cluster. The platform owner decided that Git is the approval: a change merged under the repository ruleset (two reviewers, code owners, signed commits, CI invariants) has already had its two-person review, and adding a second, cluster-side approval would make Git no longer the source of truth. The rule is therefore:

Rule Create, update and delete through Git need no cluster-side approval; the Argo CD application and ApplicationSet controllers are gitopsControllers and exempt, and every Git-driven deletion of a critical object is alerted (GitOpsCriticalDeletionApplied) so it can be matched to its PR. Everything out of band on a critical object, by anyone, needs request + two approvals + executor. The Argo CD UI/CLI is out of band (it acts as argocd-server, which is a trusted mutator but never a gitopsController).

What this shifts: the repository controls (Chapter 11) and the controller identity become the crown jewels. Hence the new residual risk R7 and its compensating controls: no-bypass ruleset, secret scanning, CI invariants that refuse argocd-server or any human in gitopsControllers, Argo CD RBAC that denies override and any create/update in the guardrails project, PrivilegedTokenMinted and PrivilegedIdentityImpersonated alerts, and the requirement that every GitOpsCriticalDeletionApplied correlates with a merged PR.

17.3 Coverage

Every control in this guide maps to at least one automated case in scripts/test-guardrails.sh (phase-aware, about sixty cases, evidence retained) or one manual case in docs/14, plus the alert that proves detection. The matrix in docs/16 §3 is the checklist for sign-off; a new control is not done until it has a row there.

18 · Impersonation control: check with --as, never change with it

Chapter 3 listed impersonation as the residual one-command bypass: admission sees only the resulting identity, never the Impersonate-* headers. The platform owner's requirement is exact: impersonation may be used only for dry-runs, client-side and server-side. Client-side dry-runs never reach the API server, so the work is on the server side. Full design: docs/17-impersonation-control.md.

18.1 The insight: real sessions carry markers that an impersonator cannot forge

SessionMarker in request.userInfo.extra
Human through OpenShift OAuth (any IdP)scopes.authorization.openshift.io (for example user:full)
Service account with a bound token (every pod, oc create token)authentication.kubernetes.io/credential-id (JTI=…, GA since Kubernetes 1.32)
Impersonated copy of eithernone, provided the impersonator cannot impersonate userextras

The impersonation filter adds extras to the assumed identity only from Impersonate-Extra-* headers, and each such header needs RBAC impersonate on userextras/<key>. cluster-admin has it (*). So the first half of the control is RBAC: nobody human holds cluster-admin.

18.2 RBAC half

  • guardrails-platform-admin: every verb on every resource and non-resource URL except impersonate, escalate and bind. Without escalate/bind the holder cannot grant themselves the missing verbs (Kubernetes' RBAC escalation check), so this is stable.
  • guardrails-impersonator: impersonate on users, groups, serviceaccounts only. Bound to platform-admins so JIT admins can still run oc auth can-i --as and --dry-run=server --as.
  • The break-glass SA is bound to guardrails-platform-admin: it needs no impersonation.
  • Only the group system:masters (the installer certificate, vaulted) keeps cluster-admin; verify-install.sh fails if any other group is bound to it or any custom role grants impersonate on userextras.

18.3 Admission half

guardrails-impersonation-dry-run-only   (all writes; access reviews and system:* components excluded)
  impersonated = (privileged SA && !hasBoundToken) || (human && !hasHumanMarker)
  allow iff     request.dryRun || !impersonated
and in every other policy:
  isExempt / isGitOps / isReaper / isOlm / isTrusted*  require the bound-token marker
  isApprover / isRequester                              require the human marker

Only privileged service accounts are marker-checked, so a tenant workload still using a legacy secret-based token is unaffected (impersonating an unprivileged SA gains nothing). Access-review groups are skipped so oc auth can-i --as keeps working. The result: under --as, reads and access reviews work, server dry-runs work and show what an ordinary user would get (no exemptions, no approver rights), and every real write is denied and alerted (ImpersonatedWriteDenied).
